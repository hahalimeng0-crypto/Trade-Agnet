# 数据库与记忆存储架构

## 最终职责边界

| 存储 | 只负责什么 | 不负责什么 |
|---|---|---|
| SQLite | 短期工作记忆、本地开发缓存、本地开发数据库 | 生产会话、长期记忆、企业知识库主元数据 |
| MySQL | 外贸与邮件、客户身份、客户/工作区完整会话、结构化长期记忆、文档元数据、索引任务 | 向量相似度检索、BM25、PDF 二进制 |
| Milvus | 企业知识库向量、客户长期记忆向量、工作区长期记忆向量 | 权威文本、权限和生命周期状态 |
| Elasticsearch | 企业知识库 BM25 子块索引 | 长期记忆主数据、文档原件 |
| 文件存储 | PDF/文本原件、解析 JSON 和 OCR 产物、回收站文件 | 文档状态和索引任务状态 |

企业知识库查询仍是混合检索：Milvus 语义召回与 Elasticsearch BM25 召回经过加权 RRF 合并，再进入后续排序。MySQL 是文档状态和权限的权威来源，Milvus 与 Elasticsearch 都是可以重建的检索投影。

## 两种运行档位

`NANOCLAW_STORAGE_PROFILE=local` 保留现有本地开发体验。业务、RAG 索引和短期工作记忆可以使用 SQLite；文档目录使用本地文件系统。

`NANOCLAW_STORAGE_PROFILE=production` 会执行强校验：

- 业务、邮件、客户身份、会话、结构化长期记忆和 RAG 元数据必须是 MySQL；
- 企业知识库向量必须是 Milvus；
- 企业知识库关键词检索必须是 Elasticsearch；
- 工作区 Markdown 长期记忆回退必须关闭。

任意一项仍指向 SQLite、JSONL、`manifest.json` 或内存后端，进程会拒绝启动，而不是静默降级。

生产参数模板位于项目根目录的 `.env.production.example`。统一连接参数 `NANOCLAW_MYSQL_*`、`NANOCLAW_MILVUS_*` 和 `NANOCLAW_ELASTICSEARCH_*` 是默认值；确有隔离需求时，模块专用参数仍可覆盖它们。

## MySQL 迁移顺序

先备份现有 SQLite、JSONL、知识库目录和 MySQL，再按下面顺序执行 DDL：

1. `agent/business/migrations/001_trade_ops_core.mysql.sql`
2. `agent/business/migrations/002_email_ingestion.mysql.sql`
3. `agent/business/migrations/003_email_accounts.mysql.sql`
4. `agent/business/migrations/004_email_delivery.mysql.sql`
5. `agent/business/migrations/005_m6_runtime.mysql.sql`
6. `agent/business/migrations/006_customer_identity.mysql.sql`
7. `agent/memory_runtime/migrations/001_long_term_memory.mysql.sql`
8. `trade_rag/migrations/002_mysql_metadata.sql`

首次以生产档位启动时，如果 MySQL 的知识库元数据为空且文件存储中存在旧 `manifest.json`，应用会幂等导入该清单。导入后 MySQL 成为权威元数据源，原文件仅保留作迁移备份，不再参与生产读写。

旧业务 SQLite、客户身份 SQLite 和历史 JSONL 不会在没有生产凭据、备份与停写窗口时自动搬迁。这是有意的安全边界：代码路径和 DDL 已完成，但真实数据切换必须在目标 MySQL/Milvus/Elasticsearch 可用后单独执行并核对行数、哈希、权限与检索结果。

## 文件路径

`NANOCLAW_KNOWLEDGE_FILE_ROOT` 指向持久卷或对象存储挂载目录。其下保持：

- `documents/`：原始 PDF、文本和图片；
- `parsed/`：解析与 OCR 产物；
- `trash/`：待治理回收文件。

生产部署必须把这个目录放在有备份的持久存储上。Milvus 和 Elasticsearch 不能替代原件备份。
