# RAG 精排序设计

## 1. 目标

精排序位于混合召回之后、最终上下文生成之前，用于从 RRF 候选池中选出与用户问题最相关、信息密度最高的内容。

本设计采用一次 LLM Listwise 调用完成候选打分，并遵循以下原则：

- 粗召回负责召回率，精排序负责相关性和顺序。
- 精排序只判断已提供候选，不引入模型自身知识。
- LLM 不可用、输出错误或解析失败时，保留原 RRF 顺序。
- 精排序不能成为 RAG 查询的单点故障。

## 2. 在检索链路中的位置

```mermaid
flowchart LR
    Q[用户问题] --> R[Milvus + Elasticsearch 召回]
    R --> F[RRF 融合]
    F --> M[多查询 RRF]
    M --> P[扩大候选池]
    P --> L[LLM Listwise 精排序]
    L --> T[截断为 top_k]
    T --> D[父块回查与内容去重]
    D --> A[生成答案]
```

精排序不直接访问 Milvus、Elasticsearch 或 PostgreSQL，只接收已经完成融合的候选结果。

## 3. 输入与输出契约

### 3.1 输入

精排器接收：

- `query`：用户问题或用于最终检索的主查询
- `results`：已按 RRF 分数排序的候选列表
- `top_k`：最终需要保留的结果数量

每个候选至少应提供：

- `content`：候选正文
- `score`：原始 RRF 分数
- `source`：候选来源

如果候选使用包装对象，也可以通过 `result.chunk.content` 提取正文。

### 3.2 LLM 输出

LLM 必须返回以下 JSON 结构：

```json
{
  "scores": [
    {"idx": 0, "score": 9},
    {"idx": 1, "score": 3}
  ]
}
```

字段含义：

- `idx`：候选在输入列表中的下标
- `score`：候选与问题的相关性和信息密度评分

设计目标要求 `score` 为 `0～10` 的整数，并且每个候选恰好出现一次。

## 4. Listwise 精排策略

本设计将全部候选放入同一个提示词中，让 LLM 同时比较不同候选，而不是逐条独立判断。

Listwise 的优势：

- 可以直接比较候选之间的相对价值。
- 一次调用即可处理整个候选池。
- 避免逐条调用产生较高延迟和成本。
- 更适合在 RRF 已经提供较好初始顺序的基础上做精调。

评分标准：

| 分数 | 含义 |
|---|---|
| 10 | 直接回答问题 |
| 7～9 | 包含明确相关事实或关键线索 |
| 4～6 | 部分相关或弱相关 |
| 1～3 | 只有共现关键词，不能支持回答 |
| 0 | 无关或噪声 |

模型只能依据候选段落评分，不允许使用自身知识补充候选中不存在的信息。

## 5. 候选池设计

如果直接把 RRF 的前 `top_k` 交给精排器，精排只能调整顺序，无法把排名稍后的优质内容提升到最终结果中。因此启用 Reranker 时，需要扩大候选池：

```text
未启用 Reranker：pool = max(top_k * 2, 10)
启用 Reranker：  pool = max(top_k * 4, 10)
```

例如最终需要 `top_k=3`，精排器可以接收最多 `12` 条候选，然后输出最相关的 `3` 条。

候选池大小需要在效果、上下文长度、LLM 延迟和调用成本之间平衡。

## 6. 提示词与内容预览

候选按照稳定下标写入用户消息：

```text
用户问题：如何配置混合检索？

候选段落：
[0] 候选正文……
[1] 候选正文……
```

每条正文最多保留 `preview_len` 个字符，默认值为 `200`。超过长度后截断并追加 `...`。

当前配置：

```yaml
rag:
  rerank:
    enabled: true
    preview_len: 200
```

截断可以控制提示词长度，但也可能丢失候选后半部分的关键信息。`preview_len` 应根据文档语言、块大小和候选池数量通过评测确定，而不是无限增大。

## 7. 排序规则

解析 LLM 返回结果后，为每个候选构造排序键：

```text
(
  llm_score,
  original_rrf_score,
  -original_index
)
```

排序优先级：

1. LLM 精排分数，高分优先。
2. LLM 分数相同时，原 RRF 分数高的优先。
3. 两种分数都相同时，保持原始候选顺序。

精排成功后：

- 将 `score` 转换为 `llm_score / 10.0`。
- 在 `source` 后追加 `+rerank`，用于结果追踪。
- 截断并返回前 `top_k` 条。

需要注意：精排后的 `score` 已不再是 RRF 分数，而是归一化后的 LLM 分数。下游不应把两者当成同一种分数进行阈值比较。

## 8. 失败降级策略

以下情况直接保留原 RRF 顺序并截断为 `top_k`：

- 候选列表为空
- 未注入 LLM 生成函数
- 只有一条候选
- LLM 调用抛出异常
- 返回内容不是合法 JSON
- JSON 中没有可解析的 `scores`

LLM 输出候选数量不足时：

- 忽略越界的 `idx`。
- 缺失候选补 `0` 分。
- 使用原 RRF 分数解决同分排序。

降级结果不应追加 `+rerank`，从而让日志和评测能够区分“真正执行了精排”与“回退到粗排”。

## 9. JSON 解析策略

虽然提示词要求严格 JSON，解析器仍兼容以下 Markdown 代码块：

````text
```json
{"scores": [...]}
```
````

解析器先移除代码块边界，再调用 JSON 解析。单个非法评分项可以跳过，不应导致整个 RAG 查询失败。

提示词约束不能代替服务端校验。稳健实现还应显式验证：

- `idx` 必须是整数并处于候选范围内。
- 每个 `idx` 最多出现一次。
- `score` 必须为有限数值。
- `score` 必须处于 `[0, 10]`。
- 如业务要求整数评分，应拒绝或规范化小数。
- 输出对象不能包含超出候选数量的大量无效项目。

当前实现已经处理解析异常、越界下标和缺失评分，但尚未强制校验分数范围、整数约束、重复下标及 `NaN/Infinity`。这些属于后续加固项。

## 10. 对象与副作用边界

当前精排器会直接修改候选对象：

- 覆盖 `result.score`
- 修改 `result.source`

这种方式开销较低，但调用方如果仍需要原始 RRF 分数，就无法从同一对象中恢复。更清晰的数据模型可以分别保存：

```text
rrf_score
rerank_score
final_score
source
```

如果暂时保持现有结构，应确保精排之后不再执行依赖原 RRF 分数的计算。

## 11. 与多查询检索的关系

Query Rewrite 可能生成多个查询。推荐顺序是：

```text
每个查询完成双路召回
  -> 多查询 RRF 合并和去重
  -> 统一执行一次精排序
```

这样可以避免每个改写查询分别调用一次 LLM，降低延迟和成本。

当前调用链使用主查询作为 Reranker 的判断问题。若改写查询包含重要限定条件，应确保主查询仍完整表达用户意图，或者在精排提示词中同时提供原始问题和规范化后的主查询。

## 12. 去重与父块策略

精排之前应尽量按稳定业务标识去重，例如 `pg_id`。精排之后、交给生成模型之前，还应按最终父块内容去重。

原因是多个子块可能属于同一个父块：

- 子块适合精确召回和精排。
- 父块适合为生成模型提供完整上下文。
- 如果多个命中子块映射到同一父块，最终上下文只应保留一份。

最终去重应发生在截断策略设计中。如果先截断再去重，可能出现要求 `top_k=3`，去重后只剩一条内容的情况。更稳健的方式是保留足够候选，逐条回查和去重，直到收集到 `top_k` 个不同父块或候选耗尽。

## 13. 可观测性

建议记录以下信息，但不要记录敏感文档全文：

- 是否启用 Reranker
- 候选数量和最终返回数量
- `preview_len`
- LLM 调用耗时
- JSON 解析是否成功
- 缺失、重复和越界评分数量
- 是否触发 RRF 降级
- 精排前后候选顺序变化
- Token 使用量和估算成本

结果来源使用以下标签区分链路：

```text
hybrid
hybrid+rerank
semantic+rerank
keyword+rerank
```

## 14. 验收标准

至少覆盖以下测试：

1. LLM 分数可以改变原 RRF 顺序。
2. LLM 同分时使用原 RRF 分数排序。
3. LLM 与 RRF 都同分时保持原始顺序。
4. 精排成功后分数归一化，并追加 `+rerank` 来源标签。
5. 空候选、单候选和未注入 LLM 时正确截断。
6. 非法 JSON、空评分和 LLM 异常时回退到 RRF 顺序。
7. Markdown JSON 代码块可以正确解析。
8. 缺失评分补零，越界下标被忽略。
9. 重复下标、负分、超过 10 分、`NaN` 和 `Infinity` 被拒绝或规范化。
10. `preview_len` 生效且不会破坏候选编号。
11. 多查询结果只调用一次精排器。
12. 最终父块去重后尽可能返回 `top_k` 条不同内容。

## 15. 最终设计边界

```text
输入：用户问题 + RRF 候选池
方法：一次 LLM Listwise 打分
主排序：LLM 相关性与信息密度分数
稳定兜底：原 RRF 分数 + 原始顺序
失败策略：回退 RRF，不中断查询
输出：最多 top_k 条精排结果
内容限制：每条候选最多 preview_len 个字符
调用次数：每次最终检索最多一次精排调用
```
